# cPanel Deployment: Entire Laravel Project in public_html

This is an alternative deployment profile for hosts where the domain document root cannot be changed from `public_html`. It places the complete Laravel repository under the document root, while using Apache rewrite rules to deny HTTP access to application source, dependencies, environment files, and private storage.

**Security note:** Keeping the project under the document root is less desirable than placing it outside the web root. The protections in `.htaccess` are mandatory, depend on the host honoring per-directory rewrite rules, and must be verified after every deployment. If the host ignores `.htaccess` or permits direct access to blocked paths, do not use this profile; move the project outside the document root.

## 1. Requirements

- PHP 8.3+ for Laravel 13, with the required Laravel extensions.
- MySQL database and a dedicated database user.
- HTTPS certificate installed before enabling the HTTPS redirect/HSTS rules.
- Apache or a compatible LiteSpeed setup with `.htaccess` and `mod_rewrite`-compatible rules enabled.
- Writable `storage/` and `bootstrap/cache/` directories.

## 2. Expected layout

Upload the Laravel repository contents directly into `/home/CPANEL_USER/public_html/` (not into an additional nested project folder):

```text
public_html/
├── .htaccess                 # root protection and routing rules from this repository
├── .env                      # create on the server; never commit or upload from Git
├── index.php                 # root Laravel front controller from this repository
├── artisan
├── app/
├── bootstrap/
├── config/
├── database/
├── docs/
├── public/                   # retained as source; direct HTTP access is denied
├── resources/
├── routes/
├── storage/
├── vendor/
├── build/                    # generated by npm run build:cpanel
└── ...
```

The domain document root must remain `/home/CPANEL_USER/public_html`. Do not put a second copy of the app in a nested folder.

## 3. Prepare and upload

On a trusted local build machine:

```bash
composer install --no-dev --prefer-dist --optimize-autoloader
npm ci
npm run build:cpanel
```

The cPanel Vite profile writes the manifest and hashed assets to the repository-root `build/` directory. Upload the complete repository contents, including `vendor/` (if Composer cannot run on the host), and the generated root `build/` directory.

Do not upload `.env`, `node_modules/`, local databases, test artifacts, or development-only secrets. Create `.env` directly in cPanel File Manager. Copy any required static public files (for example, `favicon.ico`, `robots.txt`, or images) from the repository's `public/` directory into the repository root so their public URLs resolve. Do not copy `public/index.php` or `public/.htaccess` over the root files.

## 4. Configure production

Create `public_html/.env` with production settings, including:

- `APP_ENV=production`
- `APP_DEBUG=false`
- `APP_URL=https://your-domain.example`
- A unique `APP_KEY`
- Correct cPanel-prefixed MySQL database, username, and password
- `SESSION_DRIVER=file`
- `CACHE_STORE=file`
- `QUEUE_CONNECTION=sync`
- `FILESYSTEM_DISK=local`
- `SESSION_SECURE_COOKIE=true`

Never commit or share the production `.env`. Keep `APP_DEBUG=false`.

## 5. Permissions and caches

Set directories `storage/` and `bootstrap/cache/` writable by the PHP process (typically 775 on shared hosting, depending on host ownership). Files should generally be 644 and directories 755.

Use the cPanel Cron Jobs interface with the hosting provider's PHP 8.3 CLI binary to run Artisan commands from the repository root. For example, after confirming the correct binary path:

```bash
/path/to/php83 /home/CPANEL_USER/public_html/artisan config:clear
/path/to/php83 /home/CPANEL_USER/public_html/artisan migrate --force
/path/to/php83 /home/CPANEL_USER/public_html/artisan optimize
```

Run migrations only after taking a database backup and confirming the production database credentials. Do not run demo seeders in production.

## 6. Mandatory security verification

After upload, request each URL below in a private browser window. Every sensitive URL must return 403 or 404; it must never return source text, JSON credentials, directory listings, or PHP output:

- `https://your-domain.example/.env`
- `https://your-domain.example/composer.json`
- `https://your-domain.example/artisan`
- `https://your-domain.example/vendor/autoload.php`
- `https://your-domain.example/bootstrap/app.php`
- `https://your-domain.example/app/`
- `https://your-domain.example/storage/logs/laravel.log`
- `https://your-domain.example/public/`

Also verify that normal routes and assets work:

- `https://your-domain.example/`
- The exact CSS and JS URLs listed in the manifest return 200 with CSS and JavaScript content types.
- HTTP redirects to HTTPS without a redirect loop.

Do not make the manifest publicly readable; Laravel reads it from disk and the browser does not need to fetch it. If any sensitive URL exposes content, stop and switch to the safer outside-document-root deployment.

## 7. Operational caveats

- The root `index.php` and `.htaccess` in this profile are distinct from Laravel's stock `public/index.php` and `public/.htaccess`.
- The application configures Laravel's public path to the repository root so Vite resolves `build/manifest.json` and generated URLs as `/build/...`.
- Re-run `npm run build:cpanel` and upload the complete root `build/` directory whenever frontend assets change.
- Private artwork uploads remain on Laravel's private local disk. Never create a public symlink for private artwork storage.
- `public/` is retained for repository structure but direct web access is denied. Copy only intended public static files to the root.
- This profile does not make shared hosting equivalent to a dedicated web root. The safest arrangement remains storing the Laravel project outside `public_html` and exposing only Laravel's `public/` directory.
